MaintAgent

A maintenance agent for industrial machines: a failure-risk model trained on sensor data, and an LLM agent that will investigate faults with tools and draft work orders for a person to approve.

Code on GitHub

  1. 1Azure PdM CSV files
  2. 2DuckDB
  3. 3SQL features from the past 24 h only
  4. 4LightGBM: risk and likely component
  5. 5Feature contributions
  6. 6Agent with tools planned
  7. 7Work order, human approval planned

What I built

  • A loader that reads the five CSV files of the Microsoft Azure Predictive Maintenance dataset into DuckDB, accepts two date formats and stops on any unreadable row.
  • All features in one SQL query: 3- and 24-hour sensor statistics, error counts, days since each component was replaced (ASOF joins), machine model and age.
  • A multiclass LightGBM model that gives the risk of failure in the next 24 hours and the component most likely to fail, with feature contributions for each prediction.
  • A z-score rule as the baseline the model has to beat, and recall at 80% precision as the operating metric.
  • A fixed 'now' (AS_OF) in the configuration, so the agent's tools will not see data from after the moment they reason about. Tool calling is already checked against Groq's OpenAI-compatible API.

A score that is too good

The first run on the real dataset scored PR-AUC 0.999. In maintenance data that usually points to leakage or an artifact of the dataset, not to a great model. I wrote an ablation that retrains on separate feature groups and on 0–24, 24–48 and 48–72 hour horizons to find what carries the score, and a test that fails if any feature reads data from after the prediction time.

13 passing (pytest)
Split
By time: train Jan–Jul 2015, test Aug–Dec 2015, one-day gap
Model metrics
Held back until the ablation explains the 0.999

Where it falls short

The agent, its tools and the work-order approval loop are not built yet. The model has only been evaluated on one public dataset.

Stack Python, DuckDB, SQL, LightGBM, scikit-learn, pytest, Groq API

Kocaeli Factory Intelligence

A predictive-maintenance prototype for production lines. Telemetry goes in; a 24-hour failure risk, an anomaly score, the signals behind it and a first maintenance action come out.

Open the live demo Code on GitHub

  1. 1Deterministic telemetry
  2. 2Feature validation
  3. 3z-score anomaly and logistic regression
  4. 4Model files as JSON
  5. 5Dashboard in the browser

What I built

  • A deterministic telemetry generator: 8 machines, 4,608 readings at 15-minute intervals and 24 failure events over six days.
  • A multivariate z-score anomaly score and a class-weighted logistic regression trained with gradient descent, both in plain JavaScript.
  • A dashboard that runs the model in the browser from JSON files, plus an optional Node.js HTTP API that serves the same model.
  • A screen that keeps the scenario label apart from the model output, so a scenario alarm cannot be read as a prediction.
  • Node's test runner and a GitHub Actions workflow that regenerates the data, retrains and tests on every change.

Split by time, report false alarms

Neighbouring telemetry rows are almost identical, so a random split leaks the future into training. I split by time, 75% for training and 25% for testing, and report the false-alarm rate next to recall, because a maintenance team pays for every false call.

Temporal 75/25 holdout on synthetic data.

Where it falls short

The data is synthetic, so these are not results from a factory. A real pilot needs historian or SCADA telemetry joined with maintenance records, and failure labels agreed with the maintenance team.

Stack JavaScript (ES modules), Node.js, GitHub Actions, Docker

Trendyol SEO description pipeline

A Python pipeline that pulls a brand's catalog from the Trendyol Seller API, writes a new SEO description for every product with OpenAI, checks each one against marketplace rules and hands the results to a person. Nothing is published automatically.

Code on GitHub

  1. 1Trendyol Seller API
  2. 2Fetch and normalize
  3. 3gpt-4.1-mini
  4. 4Rule checks, up to 2 retries
  5. 5Review sheet
  6. 6Human approval

What I built

  • Catalog fetch and normalization into a working spreadsheet, with retry and rate-limit handling.
  • Rule checks on every output: empty text, HTML, ten banned claims such as 'en iyi', 'garanti' and 'tedavi', and fewer than 100 words. A failed description is regenerated up to two more times, then kept as FAIL so the reviewer sees it.
  • A review sheet that puts the original description next to the new one and its status.
  • A second mode for long product pages that stores every generation in SQLite with a version number and a JSON validation report.

A person signs off

Marketplace rules punish exaggerated and medical claims, and a language model will sometimes make them. Automated checks catch the obvious failures; publishing stays a human decision, so the pipeline ends in a review sheet instead of an upload.

Where it falls short

The checks are automated; whether a description was good enough was a person's call, and there is no quality score beyond that. Client data is not in the repository.

NeoBioAI

Predicts binding affinity (pKd) from a molecule's structure with a graph neural network, served through FastAPI and a Next.js interface that shows which atoms drive a prediction.

Code on GitHub

  1. 1SMILES string
  2. 2Atom-bond graph (RDKit)
  3. 3GINEConv network
  4. 4pKd and atom explanations
  5. 5FastAPI and Next.js

What I built

  • A 4-layer GINEConv network on molecular graphs with bond features, 340,481 parameters, trained with early stopping.
  • A FastAPI backend for single and batch CSV prediction, and a Next.js interface that highlights the atoms behind a prediction.
  • An LLM-written summary report for each batch.

Say what the model ignores

The model only sees the ligand, not the protein, so it predicts one value per molecule whatever the target. An earlier README compared it with docking; I removed that comparison because the two do different things.

Clinic AI chatbot

A Turkish customer-service chatbot for dental and aesthetic clinics. It answers questions on services, prices and opening hours from the clinic's own profile, never diagnoses, and sends appointment requests to WhatsApp.

Code on GitHub

  1. 1Browser chat
  2. 2FastAPI /chat
  3. 3Input checks
  4. 4Clinic profile to system prompt
  5. 5gpt-4o-mini

What I built

  • A system prompt built from a clinic profile in JSON, so a new clinic is a new file, not new code.
  • A server that does not trust the history the browser sends: system messages from the client are dropped, messages over 1,000 characters are rejected and each IP gets 20 messages a minute.
  • Errors are logged on the server, and the patient sees a plain message.

Don't trust the browser

The conversation lives in the browser, so anyone can edit it. Keeping only user and assistant turns stops a visitor from rewriting the clinic's rules from the developer console.

Where it falls short

The tests cover input handling, not answer quality. There is no evaluation set of patient questions yet.
